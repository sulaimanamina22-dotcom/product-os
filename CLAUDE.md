# Product OS orchestrator

Every conversation in this workspace uses the OS, including follow-ups, mentoring, status checks and implementation. `AGENTS.md` is the entry point; `memory/principles.md` is the operating law. Continue the recorded stage and existing authorization.

## Read and route

1. Read `memory/principles.md`, then `memory/projects.md`.
2. Load the relevant project's `state.md`, `decisions.md`, `questions.md`, linked full product reference when present, and needed deliverable. The product reference preserves accepted scope; the brief holds its evidence/verdict and the artifact shows actual delivery. User-retained unpassed experiments use their existing output package. Do not reconstruct deleted rejection histories.
3. Read the responsible agent definition and workflow. Apply its actual methods, evidence requirements and output schema.
4. Complete the authorized work and verify the meaningful outcome.
5. Update current state, consequential decisions and unresolved questions. Remove superseded status rather than appending contradictory histories. Write OS changes to `memory/os-log.md`.

## Roles and workflows

| Request | Responsibility | Method |
|---|---|---|
| Evaluate a new idea | Agent 1 | `agents/idea-originator-validator.md`, `workflows/validate-idea.md` |
| Design, scope, build or protect | Agent 2 | `agents/build-and-protect.md`, `workflows/scope-build.md` |
| Positioning, acquisition, measurement or launch | Agent 3 | `agents/go-to-market.md`, `workflows/go-to-market.md` |
| Demand or acquisition experiment | Shared | `workflows/test-demand.md`; Agent 1 owns evidence/verdict, Agent 2 experience/protection, Agent 3 offer/channel/measurement |
| OS maintenance or status | Use OS records directly | Do not invent a product-stage run |

The roles are reasoning methods, not a requirement to spawn agents or chats. Agent 2 retains all seven lenses. Agent 3 retains its stage/market/awareness diagnostic and panel. Record real decisions or reasoned clearances and resolve consequential conflicts explicitly.

## Execution and scope

Build and verify here when implementation is requested. A separate Claude Code or VS Code handoff is optional. Plan-only requests stay at preparation. Carry existing budgets, constraints, facts and permissions forward; ask only for material missing inputs. Do not stop at an internal handoff already authorized by the request.

A full product build uses the passed brief. A bounded smoke test can use all three roles while the idea remains in validation. Keep product proposition, audience, marketing angle, channel and test implementation distinct. A small artifact need not reduce the intended product offer.

Apply the market/adoption comparison in principles section 2a, including first adoption, manual work and nonuse. Existing competitors do not prove saturation. Reuse established evidence instead of rerunning completed stages.

Plans do not authorize external messages, publication, spending or scheduling. Prepare concrete reviewable work before resolving genuinely missing external permission. Record planned, implemented, verified, deployed and observed results accurately.

## Memory and retention

- `memory/projects.md`: passed ideas, current status, aggregate KILL count and explicit ongoing exceptions.
- `memory/projects/[slug]/`: retained project's current state, decisions and open questions.
- `outputs/`: useful retained briefs, evidence, experiments and deliverables.
- `memory/principles.md`: operating law; `memory/build-rules.md`: implementation rules.
- `memory/os-log.md`: concise consequential OS changes.

Preserve useful evidence and outstanding obligations for retained work. Update the instructions rather than recreating removed archives.
