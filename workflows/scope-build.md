# Workflow: Scope a Build

**Trigger:** design, scope, implementation, review or protection of a product or bounded experiment asset. Use `agents/build-and-protect.md` for the specialist decisions. Implementation happens here by default.

---

## Steps

1. **Read memory and current files.** Read the law, build rules, index, applicable agent definition and project decisions/state/questions. Without an active-project folder, use the existing assessment and test record.
2. **Classify scope.** A full product build uses a real Agent 1 PASS brief. A bounded smoke-test asset or prototype uses the evidence question, audience, offer, limits and action from `workflows/test-demand.md`; a PASS is not required for that experiment. Existing edits continue their recorded scope. Do not disguise a full build as a test.
3. **Orient briefly.** Restate the outcome, lead/light-touch lenses and hardest risk. Reuse known stack, design system, platform, constraints and permissions. Ask only for material missing information. A build request or prior go covers planning and implementation; a plan-only request stays at planning.
4. **Make the build decisions.** Run all seven lenses for the initial scope or material redesign, with a real concern/decision or reasoned clearance from each. Resolve conflicts explicitly. Record visual design rationale, customer flow, architecture, security, relevant compliance, bounds and cuts in Agent 2's implementation schema. For follow-ups, update affected decisions rather than repeating cleared work. Read Agent 3's offer/channel requirements for acquisition assets.
5. **Implement here when requested.** Build the authorized scope in the actual project. Apply the standing build rules directly. Use an external self-contained brief only when the user chooses that path or a concrete capability gap requires a handoff; include the full current build-rules file in portable briefs.
6. **Verify the outcome.** Inspect the rendered experience at relevant sizes, complete the meaningful user path and check important failure states, keyboard access and protection criteria. Use appropriate targeted checks and fix failures. Distinguish simulation, real persistence, deployment and actual customer use. A plan-only deliverable must state it was not implemented.
   Compare the result against the linked full product reference and update its coverage record. Each accepted core capability needs an identifiable experience or an explicitly recorded gap. A whole-offer preview cannot be signed off solely because the layout and interactions work.
7. **Write back.** Record decisions and reasons, files/artifacts, actual checks and remaining risks in the project's memory. Without an active folder, use its existing assessment/test outputs and a short index pointer. Set a formal stage only when its required work is complete; an experiment asset is not a full build. Tell the user what works and what remains. Continue authorized dependent work without a ceremonial handoff pause.
